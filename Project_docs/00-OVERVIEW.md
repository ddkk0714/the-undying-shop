## 1. 한 문장 정의

> **당신은 죽음을 파는 방송국 사장이고, 스타에게 갈림길을 알려주는 유일한 사람이며, 그 지도는 당신이 직접 팠기 때문에 언제든 거짓말할 수 있다.**

플레이어가 게임 내내 반복하는 진짜 행동은 하나다: **"이 사람을 얼마나 깊이 밀어 넣고, 무엇을 감출 것인가."**

## 2. 데모 스코프 확정 (원본 기획서 대비 변경점)

원본 "2주 스코프"를 **6일**로 재단했다. 아래가 최종 확정 스코프다.

### 2-1. 확정 변경 사항

| 항목 | 원본 | **데모 확정** | 이유 |
|---|---|---|---|
| 총 일수 | 12~15일 | **8일** | 심사자 플레이 시간 10분 내 완주 |
| 1일 길이 | 90초 | **가변** — 생방송은 용사가 죽을 때까지 | 깊이 갈수록 방송이 길어지는 게 자연스럽다 |
| 시작 최고층 | 29F | **26F** | 8일 안에 40F 도달 서사를 만들려면 일당 +1.5~2F |
| 목표 | 40F | **40F 유지** | HUD `n / 40` 게이지가 핵심 도파민 |
| 시체 등급 | 5단계 | **2단계 (온전 / 훼손)** | 원본 결정 유지 |
| 엔딩 | A~D | **B(폭로) 1개 + A(개문) 짧은 분기** | B는 필수, A는 40F 도달 시 30초 컷 |
| 스타 정원 | 미정 | **동시 보유 3명, 신인 풀 상시 2명** | UI 3칸으로 고정 |
| 페르소나 | 여러 개 | **2개 (「불꽃의 리온」, 「무명」)** | 승계 1회 체험이면 충분 |

### 2-2. 시간 압박 원칙 (v3)

**어떤 선택에도 제한시간이 없다.** 타이머 바를 두지 않는다.

대신 **생방송 중에만** 지체 페널티가 있다 — 선택 대기 3초를 넘기면 **초당 시청자가 조금씩 빠져나간다**
(한 선택당 최대 -8%). HUD의 시청자 수가 내려가는 것만 보이고, 경고 문구는 없다.

- 압박은 있되 게임오버는 없다. 심사자가 UI를 읽느라 늦어도 아무것도 망가지지 않는다
- 편성실·검시실·발표에는 페널티조차 없다. 얼마든지 생각해도 된다
- 옵션 `연출 감소`를 켜면 지체 페널티도 꺼진다 (접근성)

**이건 타협이 아니라 설계다.** 시간을 재는 게임이 아니라 판단을 재는 게임이다.

## 3. 코어 루프 — 하루 사이클 **6단계** (v3)

```
[TITLE] → [DAY n]
   ① REVIVE    소생실    ~10s   어제 죽은 용사를 살릴지 / 갈아끼울지
   ② OFFICE    편성실    ~25s   계약서 심사 + 오늘의 출연자 + 진열대 3칸  (3-in-1)
   ③ LIVE      생방송    가변   1인칭 전투 3택 + 무전 + 채팅   ★핵심 · 시간 제한 없음
   ④ DEATH     사망/정산 ~10s   지지직 노이즈 → 최고층 갱신 → 일일 정산
   ⑤ AUTOPSY   검시실    ~10s   온전 / 훼손 (비공개)
   ⑥ ANNOUNCE  발표      ~5s    "회수 성공" / "회수 실패" 공표 (거짓말 가능)
→ [DAY n+1] ... → [DAY 8] → [ENDING]
```

**생환은 없다.** ③에서 용사는 반드시 죽는다. **언제 죽느냐만** 플레이어가 조작한다.

### v3에서 바뀐 것 (v2 대비)
| v2 | v3 | 이유 |
|---|---|---|
| ② 캐스팅 + ③ 진열대 (2단계) | **② 편성실 1단계** (계약심사·캐스팅·진열) | 「누구를, 어떤 장비로」는 한 화면에서 정하는 게 자연스럽다 |
| 계약 개념 없음 | **계약서 심사 추가** | 가게에 오는 사람은 손님이 아니라 지원자다 |
| ④ 생방송 30초 고정 | **③ 생방송 시간 제한 없음** | 깊이 갈수록 방송이 길어지는 게 맞다 |
| 무전 3택만 | **1인칭 전투 3택 + 무전 3택** | 주제(살릴 것인가 팔 것인가)를 한 런에 열 번 반복 |
| 층수 = 장비의 `depth` 합 | **전투 스탯(HP/ATK/DEF)** | 1인칭 전투로 바뀌었으므로 |

### 3-1. 각 단계가 만드는 압박

| 단계 | 자원이 나가는가 | 정보가 새는가 | 여론이 움직이는가 |
|---|---|---|---|
| ① 소생 | **골드 대량 유출** | — | — |
| ② 편성 | 계약금 유출 / 진열 판매로 유입 | — | 인기 페르소나 미출연 시 팬 감소 |
| ③ 생방송 | 슈퍼챗 유입 | **진실 목격 + 어필 시 유출 위험 ×1.5** | **채팅 여론 · 지체하면 시청자 이탈** |
| ④ 사망 | — | 사망 층이 곧 목격 깊이 | 최고층 갱신 시 팬 급증 |
| ⑤ 검시 | 유품 확보 | **훼손 = 진실 삭제** | — |
| ⑥ 발표 | — | — | **회수 실패 누적 = 지원자 고갈** |

이 표가 게임의 전부다. 모든 모듈은 이 표의 어느 칸을 담당하는지 명시해야 한다.

## 5. 핵심 시스템 6개 (독창성 방어선)

### 5-0. 1인칭 전투 3택 (M06) — ★ v3 신규, 최우선
용사가 인카운터마다 묻는다. **공격 / 방어 / 어필하기.**

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| 공격 | 적 HP 감소 | 55% 반격 |
| 방어 | 피해 ×0.25 | 턴 소모 · 방송이 지루해져 팬 소폭 감소 |
| **어필** | **팬 급증 + 슈퍼챗 확정** | **55% 확률로 피해 ×1.4** · 18F 이하면 **진실 유출 위험 ×1.5** |

**공격과 방어는 그를 살리는 선택이고, 어필은 그를 파는 선택이다.**
검시실에서 하루 한 번 겪는 딜레마를, 전투에서는 한 런에 열 번 겪는다. 이게 v3의 핵심 추가다.

### 5-0b. 계약서 (M05) — ★ v3 신규
용사가 **자기 손으로 쓴** 계약서를 제출한다. 「31F까지 100% / 35F까지 25%」.
**이 숫자는 사실이 아닐 수 있다.** 숨은 `honesty` 값이 과장·겸손을 만든다.

> 플레이어는 무전으로 거짓말하고, 용사는 계약서로 거짓말한다.

계약 조건은 한 줄이다 — **「시체는 반드시 회수한다. 대신 방송 중 나의 프로듀스를 따른다.」**
이게 무전 시스템의 법적 근거이자, 마왕이 300년간 해온 거래의 축소판이다.

### 5-1. 무전 (M06) — ★ 최우선
갈림길에서 **플레이어만 진짜 지도를 본다.** 3택: 왼쪽 / 오른쪽 / 나도 몰라.
- 진짜 정보를 주면 → 스타가 깊이 감 → 수입↑ **그리고 진실 목격↑**
- 거짓말하면 → 얕은 층에서 죽음 → 수입↓ **하지만 안전**
- 「나도 몰라」 → 50% 랜덤 + 팬 신뢰도 소폭 하락
- **거짓말은 즉시 들키지 않는다.** 부활한 스타가 다음날 무전에서 "어제 그 길 막혀 있던데요?" 라고 말한다. (지연된 죄책감)

### 5-2. 검시실 (M09)
사망 시체를 **온전 / 훼손** 판정. 비공개 정보.
- 온전 → 부활 가능, 팬덤 유지, **그가 본 것을 다음 방송에서 말한다**
- 훼손 → 유품 확보, 페르소나 승계 가능, **진실 삭제**, 스타 상실

### 5-3. 발표 (M09)
검시 결과와 **다르게** 공표할 수 있다. 온전히 회수해 놓고 "실패했습니다"라고 말하는 것.
- 서류상 죽은 스타 = 팬덤에서 사라지지만 골드 없이 보유 가능
- 회수 실패 공표가 누적되면 신인 지원자가 끊긴다 (캐스팅 고갈)

### 5-4. 채팅 (M07)
생방송 중 우측에 실시간 흐름. 진실 감지 댓글은 [삭제] [차단] 가능.
- 방치 → `leak` 상승, 슈퍼챗 감소
- 과잉 삭제 → 평판 하락 ("사장 요즘 왜 이럼")
- **삭제 자체가 클릭 리듬을 만든다.** 30초 구간의 손이 쉬지 않게 하는 장치

### 5-5. 페르소나 승계 (M03)
「불꽃의 리온」은 사람이 아니라 자산이다. 몸이 훼손되면 다른 시체에 이름을 씌운다.
- 팬덤·굿즈 매출·인지도는 페르소나에 귀속, 스탯은 몸에 귀속
- 승계 시 팬 일부 이탈 + "뭔가 달라진 것 같은데" 채팅 발생

## 7. 비주얼 규약 (전체 모듈 공통 강제)

### 7-1. 팔레트 — **1비트 디더 · 지정 3색** (v3.1 아트 개편)

기획자 지정색 3개가 전부다. **중간 계조는 색을 늘려서 만들지 않고 디더링으로 만든다.**

```ts
export const PALETTE = {
  ink:   0x0F1F17, // ★지정 · 배경 · 그림자 (초록기 도는 검정)
  mid:   0x3A3C31, // ★지정 · 캐릭터 중간색 · 융기 패널 · 비활성
  bone:  0xC2C8A5, // ★지정 · 시스템 전반 (텍스트 · 라인 · 밝은 면)

  dust:  0x68735E, // 파생 — bone/ink 50% 디더의 근사치. 보조 텍스트 전용
  wax:   0xC0392F, // 강조 — 화면에서 유일한 유채색 (LIVE · 소생 · 위험 · 봉랍)
} as const;
```

**규칙**
1. 어떤 모듈도 이 5토큰 밖의 색상값을 쓰지 않는다. `dust`는 텍스트에만, `wax`는 아껴서.
2. **명암 단계가 더 필요하면 색이 아니라 디더 패턴을 쓴다.** (Bayer 4×4 / 8×8)
3. 강조는 색이 아니라 **빛의 양**으로 한다.

**폐기된 토큰**: `soot` `ash` `clay` `line` `tallow` `spirit`.
- `soot`/`ash`/`clay`/`line` → `ink` / `mid` 로 흡수
- `tallow`(골드) → `bone`. 레퍼런스에서 금액도 시스템색으로 쓴다
- `spirit`(소생실 전용 청록) → **삭제.** 소생은 이제 `wax` 다 (레퍼런스의 붉은 「蘇生」 버튼)

### 7-2. 등급 표기 — 색이 아니라 테두리

| 등급 | 표현 |
|---|---|
| S | `bone` 4px + 외곽 1칸 디더 글로우 |
| A | `bone` 4px |
| B | `dust` 2px |
| C | `dust` 2px 점선 |
| F | `wax` 2px + 균열 오버레이 |

### 7-3. 도트 규약 (v3.1)

- 기준 해상도 **1920×1080**. 아트는 이 해상도에서 1비트로 디더링해 그린다
- 코너 라운딩 **0**, 보더 **2px 하드** (1920 기준. 480 시절의 1px에 대응)
- 안티앨리어싱 전면 금지 (`antialias:false`, `pixelArt:true`, `roundPixels:true`)
- 모든 좌표는 **정수**. `Math.round()` 강제. 서브픽셀 배치 금지
- **디더 격자는 화면 전체에서 같은 위상**을 쓴다. 에셋마다 격자가 어긋나면 싸구려로 보인다
- 영웅 상반신 실루엣 **384×480** (구 96×120 ×4)
- AI 일러스트 사용 시 → **1비트 양자화(ink/bone) + 오더드 디더** → 1920×1080 기준으로 정렬.
  캐릭터의 중간 면적에만 `mid` 를 허용한다

### 7-4. 봉랍 도장 = 이 게임의 시그니처

- 로고 / 커서 / 버튼 프레스 이펙트 / 검시 확정 연출이 **전부 같은 모티프**
- 확정 액션(⑥⑦)에서는 화면이 1프레임 멈추고 붉은 도장이 **쾅** — 8프레임 스프라이트 + 화면 흔들림 2px + 저음 임팩트

### 7-5. 반전을 지키는 규칙 (아트 디렉션 강제)

> **지상 사람들을 절대 이질적으로 그리지 말 것.** 평범하게, 오히려 정겹게.

캐릭터 초상, 채팅 어투, 스타 프로필 — 전부 "친근한 방송 생태계"로 그린다.
그래야 28F가 아프고 A엔딩이 무너진다. 이건 취향이 아니라 **기능 요구사항**이다.

## 8. 화면 레이아웃 (**1920×1080**)

### 8-1. 공통 HUD (상단 144px, 항상 표시)

레퍼런스 기준. **한 줄 띠가 아니라 「액자 박스 2개 + 도구 띠」** 다.

```
┌ 상태 ────────┐┌ 자원 ───────────────────┐┌ 도구 ───────────────────────────┐ y=0
│ DAY 12       ││ GOLD    FANS    REPUT.  ││  ◷    FRI      ▣ ▶    ▤ ▨ ☻ ⚙  │
│ LIVE ◆(wax)  ││ 12,840G 84.2K   B+(wax) ││ 시계  12/13   저장 불러오기 ...   │
└──────────────┘└─────────────────────────┘└─────────────────────────────────┘ y=144
   x 8..760                                    x 768..1912
```

- 좌: `L.hudStatus` — DAY / LIVE 표시등 / 자원 3종. 세로 구분선으로 칸을 나눈다
- 우: `L.hudTools` — 시계·요일/날짜·저장/불러오기·장부·도감·프로필·옵션 아이콘
- 라벨은 16px `dust`, 값은 32px `bone`, 위험/생방송 표시만 `wax`

### 8-2. 상점 화면 — **2분할 + 하단 4택** (v3.1 신규 · 레퍼런스 정본)

①소생 ②편성(계약·진열)은 **각각 다른 방이 아니라 같은 가게 화면의 모드**다.
좌측 인물과 우측 작업대는 그대로 두고 **하단 4버튼으로 모드만 갈아탄다.**

```
┌───────────────────────┬──────────────────────────────────────┐ y=144
│                       │  ☼램프          ┌────┬────┬────┐      │
│    [ 방문자 / 출연자 ]  │                 │진열1│진열2│진열3│      │
│      전신 초상          │   ▤ 장부         └────┴────┴────┘      │
│      (mid 중간톤)      │                        ✎도장  ⌗두루마리 │
│                       │   🏷가격표                            │
│  L.guest 0..752       │   L.bench 768..1920                  │ y=936
├───────────────────────┼──────────────────────────────────────┤
│ "...강한 무기 있나요? ▼"│ [蘇生] [販売] [交渉] [出撃]            │
│  L.dialogue           │  L.actions — 4칸 균등                 │ y=1080
└───────────────────────┴──────────────────────────────────────┘
```

| 하단 버튼 | 액션 | 대응 단계 |
|---|---|---|
| **蘇生** (wax) | `REVIVE/PAY` `REVIVE/SKIP` | ① 소생 |
| **販売** | `OFFICE/PLACE` | ② 진열 |
| **交渉** | `OFFICE/CONTRACT_ACCEPT` `..._REJECT` | ② 계약 심사 |
| **出撃** | `OFFICE/CONFIRM` | ③ 생방송 시작 |

- 대사는 **좌측 하단 한 줄 + `▼` 계속 표시**. 말풍선을 쓰지 않는다
- 진열 3칸은 작업대 **위쪽**에 놓는다(`L.slot3`). 램프·장부·도장·가격표는 배경 오브젝트다
- 리듀서의 `PhaseId` 는 그대로 6단계다. 이 화면은 REVIVE/OFFICE 두 단계를 **보여주는 방식**만 합친다

## 10. 절대 규칙 (Codex/Claude Code가 어기면 안 되는 것)

1. **`src/core/` 안에서 `phaser`를 import 하지 않는다.** 코어는 순수 TS이고 vitest로 테스트된다.
2. **`content/` 안의 JSON을 코드에서 하드코딩으로 복제하지 않는다.** 밸런스 상수는 전부 JSON에서 온다.
3. **에셋을 파일 경로로 직접 참조하지 않는다.** 반드시 `Assets.key('...')`를 거친다 (M03/03-ASSET-MODULES).
4. **`Math.random()` 금지.** 반드시 시드 RNG(`core/rng`)를 쓴다. 재현 가능한 버그 리포트가 6일 일정의 생명줄이다.
5. **팔레트 5토큰(ink·mid·bone·dust·wax) 밖의 색상값을 쓰지 않는다.** 중간 계조는 디더링으로 만든다.
6. **좌표는 항상 정수.** 소수 좌표 배치 금지.
7. **한 모듈이 다른 모듈의 내부 상태를 직접 수정하지 않는다.** 반드시 `dispatch(action)`.
8. **P0가 전부 녹색이 되기 전에는 P1 코드를 작성하지 않는다.**
9. **자기 소유가 아닌 파일을 수정하지 않는다.** 소유권 표는 `Project_docs/07-PARALLEL-DEV.md` §3.
10. **`types.ts` / `actions.ts`(계약 파일)는 CCR 절차 없이 고치지 않는다.** (`07-PARALLEL-DEV.md` §5-2)
